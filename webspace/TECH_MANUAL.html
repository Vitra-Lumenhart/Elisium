Webspace Federation · revision 7

1. Architectural isolation

The five entry points share a GitHub Pages root and explicit named-arrival protocol. They do NOT share global mutable JavaScript contexts, WebGL resources, browser storage keys or any backend. Legacy Gerudo and Gringotts share immutable engine source files but have distinct HTML launches. The modern Chuzhoy standalone and independent Witch/Elisium renderers are kept intact. A WebGL2 feature test selects older Garden Canvas fallback and a reduced Witch survey in GPU-restricted environments; these do not imply complete native feature parity.

index.html → iframe(worlds/*/index.html)
worlds/chuzhoy/index.html → garden_native.html (6.2.5.1)
worlds/fortress/index.html → shared/legacy/*.js (v3)
worlds/gringotts/index.html → shared/legacy/*.js (data-start-world=gringotts, with optional named tag)
worlds/witchs-hole/index.html → witchs-hole.js (v2)
worlds/elisium/index.html → elisium_native.html (v4.6)

2. Portal protocol

The shared UI uses explicit navigation to named worlds; the native legacy portal onLocal handler was minimally adapted to load sibling world pages. Witch's exit now loads ../chuzhoy/index.html?ws_v=1&ws_entry=chuzhoy-north. Only public arrival names travel. Source world time, saved journal and login state are not transmitted. Custom world mechanisms remain their own authority.

3. Geometry and provenance

H01–H24 proxy GLBs are generated with primitive triangle meshes and guaranteed to be real glTF binaries, not symbolic filenames. All source URLs are candidates from the 24-object curator table, with asset-status set explicitly to placeholder. No original Poly Haven binaries are included. Upstream v0.6 package is known by filename and size but could not be exported from the project Library on this run. Cathedral Rev06 is archived unmodified inside assets/cathedral/ with model and original CAD.

4. Self-contained right-pane preview

The generated webspace_standalone_preview.html contains gzip/Base64 source payloads for the five runtime presentations. In a GPU-disabled sandbox, it launches the v3 Garden fallback, legacy Gringotts/Fortress, reduced Witch Canvas survey, and v4.6 Elisium. In Chromium page.set_content, all five switched with zero page errors. The standalone preview is distinct from the editable GitHub Pages source tree.

5. Reproducibility and validation

Run node tests/test_unified.mjs and run existing legacy JS tests inside shared/legacy. Run python -m http.server 8000 at repository root and test the Garden, fortress, bank, Witch and Elisium in Chromium. WebGL contexts may be disabled by browser policy; Canvas fallback exists for the relevant engines. Check browser console and navigation behavior before claiming complete GPU validation.

5. Hosted deployment

Upload full repository root to the Webspace repository. GitHub Pages from main/(root). Prefer coherent, atomic commits. Preserve this README and TECH_MANUAL covenant. Avoid checking private keys, customer data, and drafts into a public repo.

5. Nested Kilns v5

worlds/elisium/kilns/ is a separately launched illustrated room graph that instantiates the full H01–H24 object manifest, with 24 per-object JSON files and a session-only discovery journal. No external assets, user login or server calls. The parent exterior exposes a doorway link; the child has a return link. Its bounded webspace:child-event postMessage only contains public discovery IDs and numeric sequence, and MUST be vetted by any listening parent for origin/source and event allowlists; no sky-state changes have been implemented in the exterior. The child's independent session clock is event sequence; a common parent/child fiction clock contract remains future work.

6. Purgatorio reserved

The Labyrinth of Purgatorio is an explicit non-playable placeholder with a world manifest. No facts, stations or gameplay have been fabricated.

7. Storage tiers and authorization

Git code and game assets vs LFS/model masters vs public Pages outputs vs private visitor-generated content vs separate durable server databases must be distinguished. The GitHub connection already has write access to Vitra-Lumenhart/Webspace, but a ChatGPT Project upload, Library file or another GitHub repository is not automatically writable simply because this public repo is. Authoring requests remain per interaction; no ongoing agent is guaranteed. Detailed notes are in docs/STORAGE_ARCHITECTURE.md and docs/CONTRIBUTOR_ACCESS.md.

10. Kilns live Poly Haven art sources — v6

The nested Kilns remains an illustrated graph, with a separate optional Three.js WebGL model study panel. When a visitor selects any H01–H24 object, assets/kilns/polyhaven-live-viewer.mjs may request the currently published 1k glTF from https://api.polyhaven.com/files/{slug}. It resolves the primary glTF plus the exact included geometry/texture URLs through GLTFLoader LoadingManager URL substitution. Domain checks restrict source file loading to the expected Poly Haven download host. Remote content has no access to the game's journal or event contract. The selected object metadata comes from the existing, authored H-object catalog.

Live artist originals are not committed as binaries in GitHub, and they are not yet spatially placed in the Kilns. The model-inspection viewer is a separate 3D canvas. The Use Webspace proxy control instead loads existing same-origin GLB placeholders; users may inspect the house story without network access. The viewport requires Three.js from a pinned jsDelivr module URL, an available graphics context, and API/CDN CORS responses. The user-visible source credit satisfies the live Poly Haven API credit requirement. The browser's origin Referer identifies the host; batch scripts send a distinct User-Agent.

tools/package_polyhaven_batch.py queries the 20 unique sources used by 24 object roles, downloads and MD5-checks all upstream 1k glTF and declared include components, then produces one ZIP with MANIFEST.json containing author, per-file SHA256 and source version hash. GitHub Actions stores the result as a review artifact; on approved main release the workflow can publish a fixed one-time GitHub Release. No manual Poly Haven upload, account, key or download is required. The frozen archive and ever-current upstream viewer serve different purposes.

Proof: tools/test_kilns_polyhaven.mjs ran successfully in Chromium on GitHub Actions for H07 live source plus its local proxy, including a journal-isolation assertion. The 20/20 source URI and CORS probe passed; batch generated a roughly 42 MB verified archive. Limits: not all 20 models received full visual QA, no in-room placement or independent parent-sky event listener has been implemented, and native Garden shader parity is not established. Refer to live art manual, source mapping and federation manifest.

Canonical editable source: Vitra-Lumenhart/Webspace → Code → main. Current publicly playable multiworld entrance: https://vitra-lumenhart.github.io/Elisium/webspace/index.html. This distinction is substantive: the webspace/v0007 GitHub Release is a frozen source artifact, not the game host, and GitHub Projects is a planning-board UI, not a count of world repositories.

The historical stand-alone Elisium repository already has GitHub Pages enabled. A controlled GitHub workflow .github/workflows/sync-webspace-mirror.yml in that repository pulls Webspace main and copies its static executable source tree under /webspace/ without altering Elisium's legacy home page. It records ORIGIN.json with the copied canonical commit. A one-time GitHub Pages build has deployed the mirror. A separate public smoke workflow verified HTTP 200 for the seven-tab entrance, all six top-level entrypoints including the reserved Purgatorio placeholder, the nested Kilns, and the pinned same-origin Three.js module. The GitHub Actions job logs are the verification record. The modern canonical Garden and all other world sources remain in the Webspace repository.

Publishing mirror state is not source authority. Accepted changes must originate in Webspace with tested source, backwards-and-forwards README/HTML manual updates, world manifests, art provenance and reviewed migrations. A new deploy request then intentionally refreshes the mirror; do not silently pull unreviewed work in the browser. A future move to a Webspace-owned Pages domain requires first-time repository-admin activation or another verified host. Until then the older Elisium repository cannot be deleted without breaking the public atlas.
